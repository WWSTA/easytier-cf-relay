## 1. 项目背景与设计目标

EasyTier 官方服务端是 Rust 单二进制（`easytier-core`），需要一台有公网 IP 的 VPS 才能自建节点。
本项目目标：**在 Cloudflare Workers 免费额度内运行一个协议兼容的 WebSocket 节点**，
让客户端（`-p wss://...`）无需 VPS 即可完成组网 rendezvous 与（可选的）数据中继。

设计原则（按优先级）：

1. **协议正确性**：字节级对齐官方实现，用真实官方客户端验证；
2. **成本趋零**：全 Hibernation API，无 setInterval 常驻；
3. **纯 P2P 优先**：节点只做控制面 + 兜底中继，鼓励客户端直连；
4. **健壮性**：幽灵节点、半开连接、重复连接、脏持久化数据都有明确处理路径。

## 3. 与官方实现的总体对比

| 维度 | 官方 easytier-core | 本实现 (easytier-cf-relay) |
|---|---|---|
| 语言/运行时 | Rust / 自托管 | JavaScript / Cloudflare Workers |
| 传输面 | TCP/UDP/WS/WSS/QUIC/WG/FakeTCP 监听 | 仅 WebSocket（Cloudflare 边缘终结 TLS） |
| P2P 打洞 | 完整（UDP/IPv6/多路径） | 不执行打洞（无 UDP 能力），仅提供 rendezvous |
| 数据中继 | 支持 | 支持（可配置关闭） |
| 路由协议 | OSPF 完整实现（本端作为节点参与） | OSPF 邻居侧实现：同步/推送/收敛由客户端 OSPF 完成 |
| KCP/QUIC 隧道 | 支持 | 转发其控制/数据包类型（不做协议转换） |
| secure mode (Noise) | v2.6.0+ 支持 | ❌ 不支持（客户端用默认模式即可） |
| 部署成本 | VPS | 免费额度内的 Workers + DO |

> 关键差异说明：本实现不参与 OSPF 最短路径计算本身，而是把客户端上报的
> `RoutePeerInfo` 原样存储并转发给同网络其他客户端（星型控制面），
> 路径计算完全由客户端的 OSPF 完成——这正是官方公共服务器在拓扑中的角色。

## 4. 协议实现详解

### 4.1 ZCPacket / PeerManagerHeader（对标 `packet/mod.rs`）

每个 WebSocket 二进制帧 = 16 字节头 + payload，全部小端：

```
偏移  长度  字段
0     4    from_peer_id   u32 LE
4     4    to_peer_id     u32 LE
8     1    packet_type    u8   (见下表)
9     1    flags          u8   (bitfield)
10    1    forward_counter u8
11    1    reserved       u8
12    4    len            u32 LE  (= payload 长度)
```

PacketType（与官方枚举值逐一核对）：

```
Data=1  HandShake=2  Ping=4  Pong=5  RpcReq=8  RpcResp=9
ForeignNetworkPacket=10  KcpSrc=11  KcpDst=12
NoiseHandshakeMsg1/2/3=13/14/15  QuicSrc=16  QuicDst=17
RelayHandshake=20  RelayHandshakeAck=21
```

flags 位（bitflags 对齐）：`ENCRYPTED=0x01 LATENCY_FIRST=0x02 EXIT_NODE=0x04
NO_PROXY=0x08 COMPRESSED=0x10 LIVENESS_PROBE=0x20 NOT_SEND_TO_TUN=0x40 LIVENESS_ECHO=0x80`。

转发语义（`peer_manager.rs`）：
- `forward_counter` 每跳 +1，**> 7 丢弃**；
- `forward_counter > 2` 时清除 `LATENCY_FIRST` 位。

> 历史踩坑：早期版本曾按 16bit 解析 packet_type（照抄了某个错误第三方实现），
| QuicSrc/RelayHandshake 枚举值也被抄错。本实现已逐一对照官方源码修正并锁定测试。

### 4.2 Protobuf：静态代码生成（关键工程决策）

Cloudflare Workers **禁止 eval / new Function**，而 protobufjs 反射模式
（`Root.fromJSON` + 运行期 codegen）恰恰依赖动态代码生成——这是第三方项目
在真机部署时报 `Codegen not supported` 的根因。

本方案：`tools/regen_proto.sh` 用 pbjs 从官方 .proto 生成**静态模块**：

```bash
pbjs -t static-module -w esm --es6 --force-long \
  --no-create --no-verify --no-convert --no-delimited --no-typeurl --no-service \
  -o src/proto_gen.js  peer_rpc.proto common.proto error.proto
```

产物仅含 encode/decode，零运行时代码生成；`--force-long` + long.js 保证
int64（transaction_id、session_id、peer_route_id）精度。

### 4.3 握手（对标 `peer_manager.rs::handle_handshake`）

请求 `HandshakeRequest{ magic, my_peer_id, version, features[], network_name, network_secret_digest }`：

1. `magic != 0xd1e1a5e1` 或 `version != 1` → 关闭连接；
2. peer_id 非法（0 / 保留 ID / 与服务端相同）→ 关闭；
3. 摘要校验：
   - 配置了 `NETWORK_SECRETS` → 用 **SipHash-1-3**（`siphash.js`，与官方
     `NetworkIdentity::digest()` 相同的算法与密钥派生）计算期望摘要并比对；
   - `STRICT_DIGEST=1` → 同网络名已有不同摘要 → 拒绝（防抢占）；
   - 否则按 `网络名:摘要` 建立分组；
4. 响应：镜像客户端 features（客户端宣告 `liveness-echo-v1` 时回显之，
   否则宣告 `SERVER_FEATURES`），`network_name` 填服务端名（与客户端不同 ⇒ 外部网络中继模式，官方公共服务器同款行为）；
5. 立即推送**全量路由**（`SyncRouteInfoRequest`），并**增量广播**给组内其他成员。

### 4.4 RPC 层（对标 `rpc_types` + `rpc/`）

分帧：`ZCPacket(payload = RpcPacket{ body = RpcRequest{ request = <inner> } })`，
响应用 `RpcResponse{ response = <inner> }` 包裹，`transaction_id`（int64）原样回传。

**descriptor 三元组语义**（对标 `service_registry.rs::ServiceKey`，实测校正）：

```
domain_name = 客户端网络名（服务按 domain 注册）
service_name = "OspfRouteRpc" / "PeerCenterRpc"
proto_name  = prost 服务短名，与 service_name 相同（如 "OspfRouteRpc"）
```

> 这是本项目实测发现的最隐蔽兼容性坑：早期实现把 proto_name 写成 `"peer_rpc"`
> （.proto 文件名），与官方 prost 生成的服务短名不符，导致客户端按
> ServiceKey 查不到服务、SyncRouteInfo 全部超时。本实现入站兼容两种取值，
> 出站统一使用官方语义。

**method_index 为 1-based**（对标 `easytier-proto/build/rpc.rs`：`Method::new((i + 1) as u8)`）：

- `OspfRouteRpc.SyncRouteInfo = 1`
- `PeerCenterRpc.ReportPeers = 1`，`GetGlobalPeerMap = 2`

压缩：本端不启用（algo=None）；收到压缩请求仅记录不处理（当前协商路径不会出现）。

### 4.5 路由同步（对标 `peer_ospf_route.rs`）

**入站 SyncRouteInfoRequest 处理**：

1. 解码 `my_peer_id / my_session_id / is_initiator / peer_infos.items[] / conn_info`；
2. 记录会话（`dst_session_id`），响应 `SyncRouteInfoResponse{ is_initiator: !req.is_initiator, session_id: 本端会话 }`（**角色取反**为官方语义）；
3. 逐条合并 `RoutePeerInfo`，合并规则（官方语义）：
   - `peer_route_id` 变化 = 新路由实例（节点重启），**无条件替换**（处理版本回退）；
   - 否则 `version` 只增不减；
4. 回推本端路由视图。

**出站推送**（全量/增量）：

- 新连接 / 会话重置 → 全量；否则仅推送 `version` 高于对端已知版本的条目；
- `RouteConnBitmap` 星型拓扑：服务端与每个已握手 peer 相连，`bitmap` 位图编码；
- **wire 层重组**（`wire.js`）：对端上报过的 `RoutePeerInfo` 保留**原始字节**，
  推送时逐字节搬运。这保留了官方未来新增字段（未知 field number）的透传能力，
  对标官方 `route_peer_wire.rs` 的 raw_peer_infos 机制；对象路径仅作兜底。

**广播时机**：新 peer 加入 / peer 离开 / 收到新 RoutePeerInfo / ReportPeers 变化。

### 4.6 PeerCenter（对标 `peers/peer_center/`）

- `ReportPeers(my_peer_id, {direct_peers: {pid: {latency_ms}}})`：
  **整体替换**该上报方的条目（官方 `server.rs::report_peers` 语义），TTL 180s 自动过期；
- `GetGlobalPeerMap(digest)`：digest 与服务端一致 → 回空响应（客户端保留缓存），
  否则回全量 `GlobalPeerMap` + 新 digest；
- digest：SHA-256(排序键+延迟) 前 8 字节 → u64。
  （官方用 `DefaultHasher`，两端无需一致——digest 只用于"变没变"的自比较，客户端总是接受服务端给的值。）

### 4.7 心跳（对标 ping/pong + liveness-echo）

- 入站 `Ping` → 回 `Pong`，payload 原样回显，from/to 交换；客户端 Ping 带自增 seq，故不能用 `setWebSocketAutoResponse` 模板应答（该 API 仅支持固定字节匹配）；
- 客户端宣告 `liveness-echo-v1`（features 镜像确认后）会在业务包上带 `LIVENESS_ECHO` flag——本实现把这些包同样视为活性信号（每条消息都会 `_touch`，天然覆盖）；
- 服务端主动探活：空闲超阈值发 Ping，半开连接因写失败触发 close 事件被立即清理。

## 5. 纯 P2P 模式

两层设计（均可配置）：

1. **`AVOID_RELAY_DATA=1`**（默认）：服务端在握手响应后的路由信息中携带
   `feature_flag.avoid_relay_data = true`。客户端 OSPF 据此给"经本节点中继"的边
   赋大代价——P2P 直连可达时绝不走中继。这正对标官方 v2.6.3 引入的
   `disable_relay_data` 哲学（控制面在，数据面绕行）。
2. **`RELAY_DATA`**：兜底开关。`1`（默认）= P2P 失败的流量仍经本节点转发
   （可用性优先）；`0` = 严格纯 P2P，丢弃 Data/Kcp 数据包只保留控制面
   （成本/合规优先）。

## 6. 幽灵节点六重防线

幽灵节点有两类：
1. **连接级**：客户端异常退出（断电/杀进程/NAT 静默丢弃）后残留的"假在线"节点——
   第三方实现最被诟病的问题（icesoulhanxi-ws-relay 的核心痛点）；
2. **路由级**：客户端多 PeerId 竞争后"被放弃的 PeerId"作为 transit 条目被其他节点转述上报，
   在路由表中留下无连接的"幽灵条目"（用户实测发现的重大 bug：实际在线只有一个连接，
   路由表却出现多个无节点在线信息的自己）。

六道防线（a–c 治连接级，d–f 治路由级）：

| 防线 | 机制 | 参数 | 延迟 |
|---|---|---|---|
| a. 握手超时 | 连接建立后未完成握手的 socket 直接关闭 | `HANDSHAKE_TIMEOUT_MS=15s` | ≤15s |
| b. 空闲超时 | 任何消息（含 ping/业务包/liveness-echo）都刷新 lastSeen；超时未刷新即清理并广播路由 | `PEER_IDLE_TIMEOUT_MS=75s`（> 客户端 ping 间隔上限 32s 的安全余量） | ≤75s |
| c. 主动探活 | 空闲超过 `SERVER_PING_IDLE_MS=40s` 服务端发 Ping；半开连接的写失败会立刻触发 close 事件 → 立即清理（不等超时） | `SERVER_PING_IDLE_MS=40s` | 秒级 |
| d. direct 覆盖规则 + reporter 追踪 | 条目按来源标记 direct（自报）/transit（他报）；**transit 永不覆盖 direct**（即使版本更高——防路由投毒/防幽灵复活）；节点（重）连时清除名下遗留条目；**上报者断开时其上报的无主 transit 条目立即清除**（唯一来源消失即失效） | — | 立即 |
| e. 路由老化 | 对齐官方 `clear_expired_peer` 两层语义：条目未刷新且节点不可达（无连接且 PeerCenter 无可达路径）超时 → 删除；未刷新超过 TTL → 无条件删除 | `ROUTE_INFO_UNREACHABLE_MS=90s` / `ROUTE_INFO_TTL_MS=3660s` | ≤90s / ≤61min |
| f. 空分组自动删除 | 分组内在线节点归零持续超过宽限期 → 整组删除（含路由条目与摘要注册，防孤儿数据） | `GROUP_AUTO_DELETE_MS=60s` | ≤60s |

清理动作统一走 `_cleanupPeer` / `cleanupExpiredRouteInfos` / `autoDeleteEmptyGroups`：
从分组移除 → 标记脏数据 → 广播增量路由（其余客户端的拓扑立即收敛）→ 落盘。

> 防线 d/e 的官方依据：easytier-core 的 `clear_expired_peer`（PeerCenter 不可达即删除）
> 与 `peer_ospf_route.rs` 的来源可信度模型。本实现在此基础上补充了 reporter 追踪
> （官方无此问题——官方服务端是 OSPF 全节点，条目天然有连接背书）。

## 7. WebSocket Hibernation 与成本设计

第三方实现（teleseon 等）用 `setInterval` 心跳维持 DO 常驻——**DO 永不休眠，
duration 费用 24×7 计费**，免费额度一天就爆。

本实现：

- `state.acceptWebSocket(ws)`（Hibernation API）+ `webSocketMessage/Close/Error` 事件处理器；
- **全程零 setInterval/setTimeout**：清扫用 `state.storage.setAlarm()`（alarm 唤醒不计 duration 费用的常驻部分，仅按一次请求计费）；
- 元数据存 `serializeAttachment()`：休眠唤醒后恢复 peerId/groupKey/lastSeen；
- `lastSeen` 双通道：内存值（运行时权威）+ attachment 节流同步（休眠唤醒后兜底）；
- 结果：空闲网络中 DO 每天仅被客户端心跳消息与 15s 周期 alarm 唤醒，
  duration 计费趋近零，免费额度内稳定运行（实测见 §11.2）。

## 8. 状态持久化

`PeerManager.toPersisted()` 序列化（节流落盘：脏标记 + ≥30s 间隔 + 成员变化短 alarm 提前触发）：

- 服务端身份（peerId/hostname——重启不变，客户端无需重新学习路由实例）；
- 各分组的 `RoutePeerInfo`（含 raw 字节）与版本号；
- 条目来源元数据（infoSource=direct/transit、reporters 集合、emptySince）——
  重启后幽灵防线 d/e/f 的判定依据不丢失（持久化格式 v4）；
- digest 注册表（STRICT_DIGEST 判定依据）；
- 会话表。

`loadPersisted()` 对损坏数据（字段缺失/类型错误）静默丢弃并继续——
DO 存储异常不应导致整个房间不可用。

## 9. KV 审计与管理端黑名单

实现模块：`src/audit.js`（`AuditStore`），由 RelayRoom DO 持有（`this.audit`）。

### 9.1 键值布局（每类信息只占一条 KV 键）

| 键 | 内容 | 说明 |
|---|---|---|
| `et-relay:rec:groups` | 网络分组事件 | create / delete（cause=admin/auto/digest-delete） |
| `et-relay:rec:peers` | 节点事件 | join / leave / replace（含 IP）。**拒绝（reject）不记录**——被拉黑客户端会不断重连，逐条记录会刷爆列表并浪费写入额度，改由 `blRejected` 计数器观测 |
| `et-relay:rec:routes` | 路由条目事件 | add（direct/transit，含"顶替 transit"）/ remove（含原因） |
| `et-relay:rec:peercenter` | 全局互联事件 | add / remove（admin / TTL expire） |
| `et-relay:rec:sockets` | 连接事件 | open / close / error（含 socketId、客户端 IP） |
| `et-relay:rec:digests` | 摘要注册事件 | register / delete |
| `et-relay:rec:admin` | 管理端审计（硬设置） | login（IP/时间，同一 IP 10 分钟去重）/ op（操作明细）。**查看（view）不记录**（v1.3.0：管理页 10s 自动刷新会刷屏且徒增写入） |
| `et-relay:bl:peer` | 节点黑名单 | 值为 PeerId；踢出节点时自动加入 |
| `et-relay:bl:group` | 分组黑名单 | 值为网络名；删除分组时自动加入 |
| `et-relay:bl:digest` | 摘要黑名单 | 值为网络名；删除摘要注册时自动加入 |
| `et-relay:bl:socket` | 连接黑名单 | 值为客户端 IP；断开连接时自动加入。**Worker 入口边缘拦截只读这一条键**（见 9.4） |

共 11 条键，全生命周期不变。记录类为定长环形缓冲（默认上限 100 条/类，
管理页「记录设置」可单独调整）；黑名单上限为硬设置（`BLACKLIST_LIMIT`，默认 1000）。
记录查询支持 `type=all`：七类记录在内存合并（每条附 `type` 字段），按全局 id
（全局单调递增 = 时间序）倒序分页——不引入任何新 KV 键；`all` 模式删除按 id
跨类型匹配，admin 硬记录永不删除。

### 9.2 三级写入路径（免费额度成本控制）

```
事件发生 ──► 内存数组（零成本）
              │  alarm 周期（15s）：脏即写 DO storage（SQLite，防休眠丢失）
              ▼
         KV 镜像 ──► 仅脏键、按 RECORD_FLUSH_MS（默认 10 分钟）节流；
                     管理端操作完成后强制刷（黑名单立即生效）
```

KV 免费额度 1000 写/天：默认间隔下每键理论最大 144 写/天；实际只在有新事件的
刷写周期产生写入，典型小网络全类合计每天数十次。读取仅发生在冷启动且 DO storage
为空时（每键一次，用于恢复）。v1.3.0 起两类高频事件不再产生写入：查看事件不记录
（原先管理页 10s 自动刷新每 5 分钟折叠一次）、黑名单拒绝不记录（重连风暴下原先
每秒可产生一条），拒绝改由 `blRejected` 内存计数器观测（零写入）。

### 9.3 硬设置与软设置

- **硬设置（wrangler.toml，管理页不可改）**：`ADMIN_AUDIT`（管理端审计开关）、
  `ADMIN_AUDIT_LIMIT`（其上限）、`BLACKLIST_LIMIT`、`RECORD_FLUSH_MS`、`RECORD_DEFAULT_LIMIT`。
  admin 类记录在管理页不可删除（防审计自擦除）；
- **软设置（管理页「记录设置」）**：六类数据记录各自的开/关与条数上限
  （存 DO storage `audit_state`，运行时生效，收紧上限时立即裁剪旧记录）。

### 9.4 黑名单拦截（双层，免费额度优化）

| 时机 | 检查类别 | 行为 | 成本 |
|---|---|---|---|
| **Worker 入口边缘层**（WebSocket 升级前，v1.3.0） | socket（IP） | KV 直读 `bl:socket` 一条键，命中 403 + `Retry-After: 60` | **不唤醒 DO**：被拉黑客户端的重连风暴只消耗 Worker 请求额度，不消耗 DO 请求与时长计费 |
| DO 升级层 | socket（IP） | 403 拒绝升级（边缘层的权威兜底，覆盖 KV 最终一致窗口内的新拉黑 IP） | 1 次 DO 请求 |
| DO 握手层（摘要校验前） | peer / group / digest | 关闭连接（4013 blacklisted） | 1 次 DO 请求 |

边缘层要点：

- `CF-Connecting-IP` 由 Cloudflare 边缘注入，客户端不可伪造（生产环境）；
- KV 为最终一致（约 1 分钟）：新拉黑的 IP 在窗口内由 DO 层兜底拦截；
  解除封锁后至多约 1 分钟内恢复可连（本地 dev 的 miniflare KV 为即时一致）；
- KV 读失败时放行走 DO 权威检查（边缘 fail-open、DO fail-closed）；
- 未绑定 `AUDIT_KV` 时边缘层自动跳过，仅 DO 层拦截（功能不变）；
- 每次 WebSocket 升级增加 1 次 KV 读（免费额度 10 万读/天，与连接数同量级，
  典型小网络占用 <5%）。

各层拒绝均**不写记录**，只递增 `counters.blRejected`（DO 层，总览页「黑名单拦截」
可见；边缘层拒绝不经过 DO，不计数，可在 Cloudflare 分析中查看）。

管理操作自动拉黑：踢出节点 → peer 类；删除分组 → group 类；删除摘要注册 → digest 类；
断开连接 → socket 类（已知 IP 时）。黑名单页支持手工添加、单个/批量移除（解除封锁）与清空。

### 9.5 事件来源（挂钩点）

- 连接/节点/分组/摘要事件：room.js 生命周期路径（`_acceptSocket` / `webSocketClose` /
  `_handleHandshake` / `_cleanupPeer`）；
- 路由与互联事件：PeerManager 纯逻辑层通过可选 `onEvent` 钩子发射
  （`route-add` / `route-remove` / `group-remove` / `pc-report` / `pc-remove`，
  带原因标签：peer-left / reporter-gone / expire / admin / reconnect），
  room 层转发给 `AuditStore`——纯逻辑层不依赖审计，单测不受影响；
- 管理端审计：Worker 入口将 `CF-Connecting-IP` 注入 `x-admin-ip` 转发给 DO，
  DO 在内部端点记录登录（同一 IP 10 分钟去重）与操作（action 明细）；
  查看（view）不记录（v1.3.0）。

## 10. 第三方项目问题与本实现的修复

| 项目 | 主要问题 | 本实现对策 |
|---|---|---|
| teleseon/cf-workers-et-ws | setInterval 心跳导致 DO 永不休眠（持续计费）；protobufjs 反射模式在 Workers 上触发 eval 限制 | 全 Hibernation + alarm；pbjs 静态代码生成 |
| icesoulhanxi-ws-relay | 幽灵节点：无握手超时、无空闲超时、无主动探活；WS_PATH 运算符优先级 bug（`'/'+env.WS_PATH \|\| '/ws'`）；不存在的 `setWebSocketAutoTimestamp` API | 三重防线；接受任意路径；attachment 元数据 |
| 21paradox / pikachuim 等 | PacketType 枚举值抄错（RelayHandshake=16 等）；proto 字段 camelCase/snake_case 混用；repeated 字段描述符写法错误；method_index 0-based | 逐字段对照官方源码修正 + 单元测试锁定 |
| （本项目自查实测发现） | proto_name 写成 `"peer_rpc"`（.proto 文件名）而非 prost 服务短名 → 真实客户端 SyncRouteInfo 全部 20s 超时（自测协议测试却通过——测试数据和实现犯了同一个错） | 出站统一服务短名；入站双兼容；**引入真实官方客户端 E2E** 防止协议自洽假阳性 |

> 经验教训已固化进测试策略：**协议实现的自测必须包含真实官方二进制**，
> 自造协议数据跑通不能证明兼容性。

## 12. 已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| 不支持 secure mode（Noise） | v2.6.0+ 的可选加密握手。收到 NoiseHandshakeMsg 包会关闭连接（4003） | 客户端使用默认（非 secure）模式即可 |
| 不执行 P2P 打洞 | Workers 无 UDP 出口。打洞由客户端之间直接进行（本节点提供 rendezvous/路由信息） | 双端均严格 NAT 时只能走中继 |
| 不做 KCP/QUIC 协议转换 | KcpSrc/KcpDst/Quic* 包仅按 to_peer_id 转发 | 无（这些包本来就是端到端的） |
| 不压缩 RPC | 出站 algo=None | 微量带宽差异，无功能影响 |
| 单房间串行（DO 单线程） | 单 DO 软限制 ~1000 req/s；更大规模需房间分片（ROOM_HEADER/QUERY） | 64 peer 默认上限内无感知 |
| IPv6 子网信息 | RoutePeerInfo 原样透传（raw 字节路径保留官方字段），但服务端自身不宣告 v6 | 客户端间 v6 组网不受影响 |
